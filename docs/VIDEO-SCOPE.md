## 1. 现有链路与根因

当前视频数据只来自 **哔哩哔哩网页公开搜索接口**；抖音、小红书、西瓜只生成官方搜索页入口，不抓取视频。

| 环节 | 改造前 |
| --- | --- |
| 前端 | `src/book/videos.js` 搜索框 / 回车 / 按钮 → `api.videos(q, 12)`；`src/views/videos.js` 是站内独立页版本 |
| 接口 | `GET /api/videos/search?q=&limit=` → `server/api.mjs` → `searchVideos()` |
| 请求 | 机械拼 3 条关键词：`q 家常做法 / q 教程 / q 详细做法` |
| 解析 | `normalizeBilibiliItem` 只保留标题、简介、作者、时长、封面；丢掉 `tag`、`typename` 等分类元数据 |
| 过滤 | 完全没有美食相关性判断 |
| 排序 | 仅标题包含关键词 + 教程/家常等弱加权 |
| 分页 | 没有分页；只取平台第 1 页，前端一次展示 |

**根因**：平台搜索本身是开放语义搜索，`开机`、`教程`、`制作` 这类词在加上「家常做法」后，仍会返回电脑、PS5、系统安装、AI 漫剧、游戏 mod 等结果；服务端不做主题校验，全部原样下发。

改造前实测（本地接口）：

- `开机` → 电脑开机自启动、Switch 开机设置、PS5 首次开机、红米笔记本开机……
- `电脑开机` → 电脑黑屏维修、Bootmgr 报错、电脑开机嗡嗡响……
- `PS5 教程` → PS 远程游玩、PS 软件教程、游戏主机教程……
- `Windows 安装` → Win7/Win10 装机、系统重装、微软商店安装……
- `制作` → 公文红头制作、AI 漫剧制作、复联小剧场制作……
- `教程` → 红烧鸡腿（正常）+ 醒图 P 图教程（无关）混排

## 2. 改造方案

服务端统一管线：

```
用户关键词
  → 关键词类型判断（明确非美食 / 模糊 / 美食）
  → 按意图生成搜索语境（不是机械拼「美食」）
  → 平台结果解析（保留标题/简介/标签/分区/作者）
  → classifyVideoCandidate 逐条分类
  → 非美食 / unknown 丢弃
  → 模糊词意图命中校验
  → 相关度排序
  → 按 id + 标题归一化去重
  → limit 截断后返回前端
```

### 2.1 关键词层

- **明确非美食**（电脑、Windows、PS5、手机、路由器、显卡、游戏攻略、AI 漫剧、影视、编程等）：直接返回 `reason=off_topic_query`，**不请求外部平台**，也不生成平台搜索入口。
- **模糊词**（开机 / 设置 / 制作 / 教程 / 安装 / 维修 / 使用 / 技巧…）：
  - 设备操作类（开机/设置/安装/维修/使用/连接）追加「烤箱 / 厨房电器 / 烹饪」语境；
  - 制作/教程类追加「美食 / 菜谱 / 烹饪」语境；
  - 结果还必须命中原始词或其同义词（如「开机」允许「首次使用/开锅/启动」），否则丢弃。
- **美食词**按类型选择语境：
  - 菜品：`做法 / 家常做法 / 菜谱`
  - 食材：`做法 / 怎么吃 / 挑选`
  - 技法：`技巧 / 教程 / 烹饪`
  - 饮食文化：`纪录片 / 文化 / 美食`
  - 设备：`使用 / 食谱 / 教程`

没有把所有关键词统一拼成「关键词 + 美食」。

### 2.2 视频分类层

`classifyVideoCandidate(item)` 检查：**标题、简介、标签、分区、作者**，输出：

`dish_recipe` / `ingredient` / `cooking_method` / `food_culture` / `food_review` / `food_processing` / `kitchen_equipment` / `non_food` / `unknown`。

规则要点：

- 标题/标签出现电脑、手机、游戏、影视、软件、宠物、农业、健康科普等明确非美食词，且没有美食标题信号 → `non_food`；
- 分区为游戏 / 数码 / 软件 / 影视 / 科教 / 宠物 / 农业等，且没有烹饪动作或设备用途 → `non_food`；
- 设备维修、拆机、电路故障 → `non_food`（即使标题里有「烤箱」「烤」）；
- 纯设备开箱/选购，没有使用或食物制作语境 → `unknown`（不展示）；
- 只有「烹饪设备」且明确是使用/食谱/开机/温度等 → `kitchen_equipment`；
- 信息不足 → `unknown`，**默认不展示**，不为凑数放行。

没有调用大模型：规则优先、成本可控；`unknown` 宁可少展示也不放行。后续若需要提高召回，可在 `unknown` 子集上增加 AI 二分类，不影响现有过滤。

### 2.3 排序、去重、分页

- 排序：标题完全匹配 > 标题开头匹配 > 标题包含 > 简介/标签包含；再做做法/教程/家常等美食内容加权；美食分类加分。
- 去重：先按平台 id，再按标题归一化（去标点/空格/表情）去重。
- 分页：新增 `page` 参数（1–5），每个关键词按页请求，**过滤、排序、去重都在分页切片之前**；前端当前没有「加载更多」，所以 UI 仍展示第 1 页，但接口分页已具备同样的过滤逻辑。

### 2.4 平台可用性

测试期间哔哩哔哩旧搜索接口对本机 IP 返回 412。已增加同一平台的 **WBI 签名搜索接口**兜底（官方网页使用的接口，返回结构一致），旧接口失败时自动切换；仍失败则如实返回错误，不伪造视频。

## 5. 已知限制

1. **依赖平台元数据**：分类依据标题/简介/标签/分区/作者；平台标题夸张或元数据缺失时可能误判。策略是「不确定就不展示」，因此个别真实美食视频可能被漏掉。
2. **没有 AI 兜底**：为控制请求成本未启用逐条模型分类；如后续要提升召回，可在 `unknown` 子集加批量 AI 判断。
3. **平台风控**：旧接口 412 时已用 WBI 兜底；若两种接口都不可用，会明确报错，不会用无关视频填充。
4. **前端没有分页/加载更多**：当前视频章节只展示第一页 12 条；接口已支持 `page` 且分页过滤已验证，未来加「加载更多」时直接透传页码即可。
5. **没有搜索历史**：当前模块本来就没有搜索历史功能，未新增。
6. **测试环境**：Chrome headless + 本地 5180；未做真机网络/移动端键盘专项（视频页输入框无复杂键盘交互）。
